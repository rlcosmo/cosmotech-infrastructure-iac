# V2-004 — AWS Power Manager

Portal privado: https://cosmotech-lab-power-manager.botanicalrook.chatgpt.site

Os dois fluxos estão implementados. **O primeiro desligamento real não foi executado**:
exige a confirmação pessoal do proprietário no portal, após inventário e plano válidos.
A certificação segura não equivale a um ciclo real de parada e religamento.

## Arquitetura Always-On

- Frontend Cloudflare Worker via Sites, acesso privado ChatGPT; não depende do EKS.
  Cloudflare Pages não estava conectado; não foi criada dependência de outra conta Cloudflare.
- API Gateway HTTP + Lambda de API, Lambda executor + Step Functions Standard.
- Controle, lock, auditoria e checkpoints no DynamoDB on-demand com PITR e proteção
  contra exclusão. TTL somente para planos/cache; operações e auditoria permanecem.
- Snapshot S3 privado, versionado, AES256 e TLS obrigatório. Referências incluem VersionId.
- State Terraform separado: `lab-v2/power-manager/terraform.tfstate`, com locking S3.
- Recuperação AWS começa pela API Lambda: inicia o host de controle antes de usar SSM/Kubernetes.
  Não precisa de Argo CD, Kestra, Grafana ou worker ativo para iniciar o religamento.

## Autenticação e IAM

O proprietário entra pela autenticação do Sites. Não há senha padrão ou credencial AWS
no browser. O Worker assina chamadas da API com HMAC, timestamp, método, caminho, hash
completo do corpo e identidade da sessão. Origem cruzada é rejeitada; acesso de serviço
sem sessão pessoal não pode confirmar operações. Chave somente em SecureString e secret
server-side do Sites, fora do Terraform State e dos repositórios.

Pipeline usa OIDC, `aud=sts.amazonaws.com`, subject imutável do repositório central e
`refs/heads/main`. A role de publicação tem autorização temporária e não altera IAM.
Bootstrap administrativo limita-se a IAM/SSM e planejamento/leitura; nenhuma chave
permanente foi criada e nenhum profile persistente foi alterado. Sessão renovada em
configuração isolada após ExpiredToken, com identidade e hash do config original verificados.

Roles de runtime são de serviço, sem root. Writes do executor:

- Start/Stop somente nas três EC2 enumeradas abaixo.
- EKS UpdateNodegroupConfig somente no node group aprovado.
- Suspend/ResumeProcesses somente no ASG associado.
- ModifyInstanceAttribute somente blockDeviceMapping dos workers com o tag de ASG
  aprovado, para preservar EBS na terminação; outras alterações de atributo são negadas.
- SSM somente documentos fixos Power Manager e três hosts conhecidos.
- Metadados operacionais somente no bucket/tabela próprios.

IAM, exclusão de dados e alterações de rede são negados ao executor. Nenhum Terraform
é executado pelos botões. O plano de publicação rejeita exclusão, substituição e qualquer
recurso fora da stack Power Manager.

O portal consulta metadados de compute, armazenamento, rede, SQS, DynamoDB, Lambda,

Recursos de serviços não cobertos e nunca marcados podem não aparecer. Recursos desconhecidos
ficam protegidos e não recebem comandos automáticos. Falha de cobertura bloqueia DOWN;

## Proteções de rede e persistência

ALB/NLB, listeners, configurações de target groups, NAT, EIPs, VPC, subnets, rotas,
Security Groups, IGW e DNS não são modificados pelos botões. Fingerprint canônico é
comparado ao final; saúde/membership de targets é transitória e não é configuração.
Não há tentativa automática de corrigir rede divergente.

O control plane EKS, frontend, autenticação, API, orquestrador, tabela e bucket de
recuperação permanecem ativos. S3, DynamoDB, EBS/EFS, snapshots, SQS/DLQ, ECR, IAM,
certificados e secrets são preservados. SQS continua com sua retenção normal: não
há receive/delete/purge pelo Power Manager. A DLQ antiga tinha 1 mensagem, retenção 14 dias;
as filas principais têm 4 dias. Parar compute não suspende TTL nem congela mensagens.

## Desligamento e recuperação

DOWN exige plano por ator, testes seguros, confirmação digitada e checkbox explícito.
A trava condicional exclui operações simultâneas; idempotência usa UUID por requisição.
Antes de qualquer mudança no laboratório são gravados snapshots de processos nas EC2,
Kubernetes, capacidades AWS, volumes e rede. Estado é revalidado contra o plano.

1. Preservar volumes de workers com DeleteOnTermination=true, alterando somente esse
   atributo para false após confirmação. Não desligar antes de concluir essa proteção.
2. Congelar processos ASG, pausar Argo, Cluster Autoscaler, Load Balancer Controller, operadores e produtores. O controller de LB fica pausado antes de reduzir workloads, preservando as configurações de rede.
3. Parar a EC2 GLPI/Kestra e aguardar duas observações sem mensagens SQS em processamento.
   Backlog/DLQ permanece armazenado, sujeito à retenção normal.
4. Reduzir workloads, aguardar término dos pods de aplicações e manter réplicas desejadas
   dos componentes bootstrap de kube-system. Nenhum PVC/Service/Ingress é excluído.
5. Liberar terminação ASG, reduzir min/desired MNG a zero mantendo max>=1 e aguardar.
6. Parar monitoramento e o host de controle por último; conferir volumes e rede.

UP exige confirmação e usa **o snapshot anterior ao DOWN**, nunca capacidades zero
redescobertas. Inicia somente EC2 que a operação tentou parar e que estavam originalmente
ligadas. Restaura processos originais, min/max/desired e workloads. Retoma Launch antes
que o ASG precise criar nós. Recupera Kyverno/Istio antes das demais aplicações, containers
existentes sem pull/recreate, Argo refresh e controladores. Não força um novo release GitOps.
Valida réplicas, imagens/templates, PV/PVC, endpoints e fingerprint de rede.

Falhas ficam RECOVERY_REQUIRED com o snapshot original preservado; LIGAR pode retomar
uma parada ou recuperação parcial. Processos ASG previamente suspensos não são reativados.
Falha antes do snapshot não executa ação de power e libera a trava. Timeouts da state machine
são reconciliados no status. Diferenças ou componentes não saudáveis não recebem falso sucesso.

RBAC aprovado/aplicado: 16 objetos, sete namespaces (`istio-system`, `kube-system`,
`kyverno`, `loki`, `observability`, `orders-api`, `orders-worker`), leitura limitada e
Scale dos 24 workloads conhecidos. Nenhum cluster-admin ou mapeamento EKS foi criado.

### Guarda de recuperação GitOps

A pausa aguarda a saída dos controladores locais do Argo CD antes de reduzir
workloads. A retomada preserva os Application specs e exige a mesma revisão
remota do GitOps registrada no snapshot. A consulta usa o deploy key existente
e os host keys fixados do Argo CD, sem copiar credenciais nem executar código
do repositório. Se main mudar durante a pausa, a capacidade e as réplicas
podem ser recuperadas, mas Argo permanece pausado e a operação informa
RecoveryRequired até revisão da diferença.

A extensão em `ops/power-manager/rbac-reader-extension.json` é somente leitura
(get/list), sem secrets ou novas permissões de alteração. A leitura global foi autorizada pelo proprietário e aplicada com sessão STS temporária; namespaces vazios não são tratados
como workloads, mas recursos fora das sete namespaces operacionais bloqueiam
o desligamento até análise das dependências.

Acesso administrador: identidade externa ChatGPT/Sites do proprietário.
Entrar com a mesma conta proprietária do ChatGPT em `/signin-with-chatgpt`; não existe senha própria do portal. A política mantém somente o proprietário autorizado.

### Ciclo controlado autorizado

O workflow `V2-004 Controlled Power Cycle` usa OIDC não-root e invocação IAM
da Lambda API. Identifica o ator como `github-actions:run-attempt`, sem simular
um visitante Sites e sem acessar a chave HMAC do portal. O backend aplica os
mesmos planos, confirmação, certificação, lock, snapshots e máquina de estados
dos botões. O teste tenta UP também após falha parcial de DOWN e registra
o incidente; nunca remove um lock ativo para forçar execução.

A descoberta global identificou seis PVCs passivos de recuperação, Bound, sem
pods consumidores e com PVs Retain. São classificados como persistentes; não
são escalados, apagados ou tratados como aplicações a desligar. PVCs sem
retenção comprovada e workloads fora da allowlist continuam bloqueando DOWN.

O teste real usa a política IAM temporária `cosmotech-power-cycle-temporary`,
com validade máxima de três horas: invocar somente a API Power Manager e listar
comandos SSM em us-east-1 para bloquear automações concorrentes. O bootstrap
administrativo apenas concede/revoga essa política; não opera computação.
Após o teste, executar `bootstrap_power_cycle_access.py revoke`. A sessão OIDC
da automação permanece separada das credenciais administrativas.

Se uma execução do GitHub for interrompida, o workflow oferece `action=recover`
para executar somente UP usando o snapshot original. A recuperação não exige
certificação DOWN, inventário global completo ou um EKS com nós. Operações
ainda ativas mantêm o lock e precisam terminar antes de uma nova recuperação.
